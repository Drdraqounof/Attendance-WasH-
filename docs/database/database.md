# Database — Neon Postgres via Drizzle

**Date added:** 2026-08-10
**Status:** Schema migrated + seeded (live on Neon). App pages still read from mock files — not wired to the DB yet.
**Provider:** Neon (serverless Postgres)
**ORM:** Drizzle ORM + drizzle-kit

## What this is

A `DATABASE_URL` (Neon connection string) was added to `.env`. This pass
builds the real Postgres schema and seeds it with data equivalent to
the mock files under `src/lib/*-mock.ts`, so the same demo dataset now
exists in an actual database.

**The UI does not read from this database yet.** `/dashboard`,
`/analytics`, `/insights`, `/dashboard/people/[id]`, etc. all still
import directly from the mock files, same as before. Wiring pages to
real queries is a separate follow-up — this pass is schema + seed only.

## Files

| File | Purpose |
| --- | --- |
| `.env` | Holds `DATABASE_URL` (git-ignored — never committed). |
| `src/db/schema.ts` | Drizzle table definitions, one per mock entity (see mapping below). |
| `src/db/client.ts` | Server-only Drizzle client using Neon's HTTP driver (`@neondatabase/serverless` + `drizzle-orm/neon-http`). Throws at import if `DATABASE_URL` is unset. |
| `src/db/seed.ts` | Seed script — imports the existing mock modules directly (`getAllPeople()`, `DEMO_MANAGER`, `POSITIVE_POINT_RULES`, etc.) and inserts equivalent rows. Idempotent: deletes in FK-safe order before re-inserting. |
| `drizzle.config.ts` | drizzle-kit config — points at `src/db/schema.ts`, migrations output to `drizzle/`, reads `DATABASE_URL` via `dotenv`. |
| `drizzle/0000_windy_blob.sql` | Generated migration — the actual DDL applied to Neon. |

## Schema → mock mapping

| Table | Mirrors | Notes |
| --- | --- | --- |
| `managers` | `manager-mock.ts` → `DEMO_MANAGER` | Single demo manager row. |
| `employees` | `dashboard-mock.ts` (`RosterEmployee`) + `people-mock.ts` (`PersonProfile`) | One row per floor employee; string IDs (`"e01"`) kept to match mock IDs. `policy_cap` defaults to **16**, seeded from `POLICY_CAP` — `people-mock.ts`'s own `policyCap` field also reads 16 now, both in sync. |
| `schedule_days` | `people-mock.ts` → `ScheduleDay[]` | FK to `employees`, cascade delete. |
| `point_events` | `people-mock.ts` → `PointEvent[]` (point ledger) | FK to `employees`, cascade delete; string IDs (`"p01a"`) kept. `rule_code` (nullable) traces an event back to a `point_rules.code` when it was generated by the policy engine. |
| `point_rules` | `src/lib/policy-engine.ts` → `ESCALATION_RULES` | The 7 real escalation rules only (duration × notice-status matrix, plus the non-attendance written-warning rule — see the policy PDF §4) — the old separate "positive points" + "deduction" catalog (`settings-mock.ts`) was retired; the model is deduction-only. `code`/`points`/`active` are populated for every row now. |
| `policy_thresholds` | `src/lib/policy-engine.ts` → `POLICY_THRESHOLDS` | The 1/4/8/12/16-point risk bands from the policy PDF §5 (low / elevated / at_risk / critical / termination). Admin-editable; seeded from the policy engine's constants today. |
| `warnings` | New — no mock equivalent | Stateful record of a threshold crossing (`open`/`acknowledged`/`resolved`), written by `src/lib/policy-queries.ts::recordPointEvent`. Distinct from `attendance_alerts` below, which is a feed, not a workflow state machine. |
| `notifications` | New — no mock equivalent | Persisted in-app notification feed (`unread`/`read`), inserted alongside a `warnings` row whenever an infraction or manual status change hits the **termination** threshold — see `src/lib/policy-queries.ts::recordPointEvent`/`setEmployeeStatus`. Read via `src/lib/notifications-queries.ts` (`getNotifications`, `getUnreadNotificationCount`, `markNotificationRead`, `markAllNotificationsRead`); read/write gated through `src/app/api/notifications/read/route.ts`. Append-only, same ledger pattern as `point_events`/`warnings` — "read" is tracked via `status`/`readAt`, rows are never deleted. **No manager FK**: since [docs/auth/authentication.md](../auth/authentication.md) has no per-manager identity (every route just checks `hasDemoSession()`), notifications are broadcast to any signed-in user rather than targeted at whoever triggered/owns the warning. |
| `automation_toggles` | `settings-mock.ts` → `AUTOMATION_TOGGLES` | Key is the natural primary key (`smsIntake`, `managerAlerts`, …). **Not actually read from — known gap:** `/settings`' `AutomationToggles` UI (`src/app/settings/automation-toggles.tsx`) persists its on/off state to browser `localStorage` only (`AUTOMATION_TOGGLES_STORAGE_KEY`), and only ever reads toggle *definitions* (label/description/default/locked) from the static `settings-mock.ts` constant, never from this table. Unlike thresholds/escalation rules (see `docs/policy/policy-thresholds-editing.md`), no route reads or writes `automation_toggles` today — the table exists in schema/seed but is otherwise dead. |
| `attendance_alerts` | `alerts-mock.ts` → `generateAttendanceAlerts()` | In the mock layer these are computed at request time from employees; here they're persisted as a snapshot so a real alerting pipeline has somewhere to write later. |

Enums: `schedule_status`, `point_source`, `alert_severity`,
`point_rule_category`, `warning_status` — all mirror the TypeScript
union types in the mock files (or `src/lib/policy-engine.ts`, for
`warning_status`) exactly.

## The 16-point escalating policy (added 2026-09-03, realigned to the official policy 2026-09-15)

See `docs/planning/points-system-brd.md` for the original business requirements (now largely superseded) and `docs/WCL_Attendance_Policy_AttendPoint_Reference.pdf` for the authoritative policy. In short:

- `src/lib/policy-engine.ts` is the pure-logic source of truth: the 7
  escalation rules (a duration × notice-status point matrix, plus a
  flat non-attendance-written-warning rule), the 5 risk-band thresholds
  (1/4/8/12/16 points — low/elevated/at_risk/critical/termination), and
  `applyPointEvent()`/`riskLevelFromPoints()`.
- `src/lib/policy-queries.ts::recordPointEvent()` is the only place that
  should write a real infraction: it inserts the `point_events` ledger
  row, updates `employees.points`, and opens a `warnings` row for every
  threshold just crossed.
- Points are evaluated on a **rolling 12-month window**
  (`src/lib/policy-queries.ts::rollingPolicyPoints`,
  `src/lib/insights-queries.ts`'s rolling-sum expressions), not an
  all-time or anniversary-reset total — per the policy PDF §5.
- Reaching 16 points (`riskLevelFromPoints` → `"termination"`) is the
  policy's termination threshold ("16 or more points requires
  termination under the policy") — this system only flags it (never
  registers points above the cap, surfaces a badge) rather than taking
  an automated termination action, preserving HR/management discretion
  per the policy document's own instruction. Surfaced today on
  `/insights`' "Employees at risk" list as a "Termination threshold"
  badge (`src/lib/insights-queries.ts::employeesAtRisk`).
- **2026-09-06 update:** the legacy mock-driven pages (`/dashboard`,
  `/analytics`, `/settings`, `/dashboard/people/[id]`) were migrated
  onto this same policy engine — `dashboard-mock.ts` now re-exports
  `riskLevelFromPoints`/`RiskLevel` from `policy-engine.ts` instead of
  keeping its own 12-point copy, and Settings now renders the real
  escalation schedule/thresholds instead of the old positive/deduction
  catalog. Full parity (a dedicated `/reports` page,
  `warnings`-table-backed KPIs, filters) is still Phase 6 in
  `docs/planning/points-system-brd.md` — this pass only unified the
  risk-level plumbing and demo data, not the reporting/analytics
  rebuild.
- **2026-09-15 update:** point values, thresholds, and the evaluation
  window were realigned to the official policy PDF (see
  `docs/planning/points-system-brd.md`'s 2026-09-15 note). Not yet
  built: leave-type accrual (Sick/Personal/Vacation/Bereavement) and
  the full restorative-process/PIP workflow (written offers, point
  cancellation) — see `docs/policy/leave-and-restorative-followup.md`.

## Commands

```bash
npm run db:generate   # regenerate SQL migration from src/db/schema.ts after a schema edit
npm run db:migrate    # apply pending migrations to the DATABASE_URL in .env
npm run db:seed       # wipe + re-insert demo data (safe to re-run)
npm run db:studio     # open Drizzle Studio against the live database
```

## Operational notes

- **Secrets**: `.env` is git-ignored (`.gitignore` → `.env*`). `DATABASE_URL` contains a live Neon password — never log it in full or commit it. `src/db/client.ts` is server-only; never import it from a `"use client"` component.
- **Driver**: uses Neon's HTTP driver (`neon-http`), not a persistent TCP socket — works from serverless/edge runtimes without connection-pool management. If a future feature needs transactions or `LISTEN/NOTIFY`, switch to `drizzle-orm/neon-serverless` (WebSocket) for that specific path.
- **Idempotency**: `db:seed` deletes existing rows before inserting, so re-running it is always safe and won't create duplicates.
- **Next step (not done here)**: swapping page data sources from `src/lib/*-mock.ts` imports to `src/db/client.ts` queries, one route at a time, is intentionally deferred to a follow-up pass.
