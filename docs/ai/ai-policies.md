# AI use policy

**Date:** 2026-10-22
**Applies to:** every AI feature in AttendPoint, now and in the future
**Related:** [ai-integration.md](ai-integration.md) (how the OpenAI
connection works) · [ai-analysis-page.md](ai-analysis-page.md) (the
`/insights` page)

AttendPoint uses AI to put attendance data into words. It does not use AI
to make attendance decisions. This document sets the rules every AI
feature has to follow, and says where today's code meets them and where
it doesn't yet.

## 1. Where AI is used today

| Feature | Where | Code | What the model does |
| --- | --- | --- | --- |
| Executive summary | `/insights`, top card | `generateInsightsNarrative()` in `src/lib/ai-narrative.ts` | Writes 3–5 sentences from numbers that were already computed |
| At-risk recommendations | `/insights`, "Employees at risk" | `generateAtRiskRecommendations()` in `src/lib/ai-recommendations.ts` | Rewords each employee's required action from the policy engine as one sentence |
| Summary refinement | `/insights/report` builder | `refineInsightsNarrative()` via `POST /api/insights/summary/refine` | Rewrites the summary to match a manager's feedback |
| PDF report | `/insights/report` | `src/lib/insights-report.ts` | Includes the summary above (no separate AI call) |

Provider: OpenAI, model `gpt-4o-mini`, pinned in
`src/lib/openai-client.ts`. All calls are made server-side.

## 2. Core rules

### 2.1 AI never decides

- **Points, risk bands, thresholds and required actions come from
  `src/lib/policy-engine.ts` and the database, never from a model.** AI
  output must not change a stored value, trigger a notification, or move
  an employee to a different risk band.
- **Disciplinary steps are human decisions.** That covers warnings,
  suspension, PIPs and termination. AI text may *describe* the step the
  policy requires. It must not recommend going beyond it, skipping it, or
  making an exception. The termination threshold stays a flag that HR
  reviews, never an automatic action.
- **The page works with no AI at all.** Every AI feature must have a
  deterministic fallback, and the numbers on screen must be correct
  whether or not `OPENAI_API_KEY` is set.

### 2.2 Grounded in our data only

- The model receives only facts the app has already computed: names,
  point totals, risk bands, counts, trends and the policy engine's
  action text.
- Every prompt tells the model to use only the numbers given and never
  invent names, numbers or dates. New prompts must include the same
  instruction.
- Structured output (JSON mode) is matched back to employees by
  `employeeId`. If an entry is missing or malformed, that employee gets
  the deterministic text instead (`ai-recommendations.ts`).
- The prompt and the on-page sections read from the same query
  functions (`src/lib/insights-queries.ts`) for the same `days` window,
  so the AI text and the numbers next to it can't drift apart.

### 2.3 Always labeled

- AI-written text must be labeled where it's shown. Today `/insights`
  shows **"Generated by OpenAI"** or **"Fallback"**, and the PDF prints
  the same label.
- Don't present AI text as policy, as HR's wording, or as a manager's
  own words.

### 2.4 Station scoping applies to AI too

- AI inputs are built from queries scoped by `session.scope`, the same
  as the page they appear on. A supervisor's prompt contains only their
  station's employees.
- Cached AI output is keyed by `days` and scope (`unstable_cache`
  includes the arguments in the key), so one station's summary is never
  served to another.
- Every AI route requires a session (`requireApiSession()`). The refine
  route also requires the mutating-request check.

## 3. Data sent to the AI provider

| Sent | Not sent |
| --- | --- |
| Employee display names and IDs | Emails, phone numbers, addresses |
| Point totals, risk bands, late-arrival counts, trends | Raw SMS text or free-text notes |
| Incident category counts (e.g. "Late: 12") | Medical, leave or protected-category details |
| Policy engine action text | Passwords, session tokens, API keys |
| A manager's typed feedback (refine step only) | Anything from `.env` |

Rules:

- **Send the minimum.** New prompts should use IDs and aggregates where
  a name isn't needed. Adding a new field to a prompt (especially free
  text, notes, or anything about health or leave) needs a review against
  this table first.
- **Never send** raw SMS bodies, medical or leave reasons, or protected
  characteristics. Attendance reasons can reveal health information, so
  only the category counts go out.
- **Keys stay on the server.** `openai-client.ts` must never be
  imported from a `"use client"` file, and the key must never be logged.
  Logs go through `createLogger()`, which redacts secrets. See
  [logging.md](../operations/logging.md).

## 4. Adding or changing an AI feature

Before merging, check that the feature:

1. Calls the model server-side only, through `getOpenAIClient()`.
2. Feeds the model only computed facts, with the "never invent data"
   instruction in the system prompt.
3. Has a deterministic fallback for a missing key, an API error, an
   empty response and malformed output, and never throws to the page.
4. Is scoped by `session.scope`, with scope in the cache key.
5. Labels its output as AI-generated in the UI and in any export.
6. Is cached or rate-limited so cost stays bounded (today: one call per
   `days` window per scope per hour, `max_tokens` capped).
7. Stays within the data table in section 3, or the table is updated as
   part of the change.
8. Is documented in [ai-integration.md](ai-integration.md).

Changing the model (`OPENAI_MODEL`) or the provider counts as a change
under this policy. Check the output on `/insights` for all three windows
(7, 30, 90 days) before shipping.

## 5. Known gaps

These parts of the code don't meet the policy yet. Each one should be
fixed or formally accepted before production.

- **No data processing agreement on record.** Employee names and
  attendance figures go to OpenAI. Confirm that WCL's OpenAI account
  terms, including data retention and training opt-out, are acceptable
  to WCL and HR.
- **The refine step isn't grounded in our data.** `POST
  /api/insights/summary/refine` accepts `currentText` from the browser
  and only tells the model not to add facts beyond that text. A user can
  send any text and get it rewritten. Fix: rebuild the summary on the
  server, or check that the text matches the cached summary.
- **The PDF label can be spoofed.** `POST /api/insights/report` trusts
  the `source` field the browser sends, so any text can be printed as
  "Generated by OpenAI". Fix: decide the label on the server.
- **No input limits or rate limiting** on the refine route. Feedback
  text has no length cap, and the route has no per-user limit, so cost
  isn't bounded (see the production checklist).
- **No output check.** Beyond the prompt instruction, nothing verifies
  that the numbers in a summary match the input. A simple check that
  every number in the output appears in the prompt would catch most
  hallucinations.
- **Uses `console.error`.** `ai-narrative.ts` and
  `ai-recommendations.ts` should move to `createLogger()`.

## 6. Ownership

- **HR** owns the attendance policy and every disciplinary decision.
  AI text never replaces their judgment.
- **Engineering** owns making sure every AI feature follows sections 2–4,
  and keeps section 5 up to date.
- Questions or exceptions go to HR and engineering together, and the
  outcome is recorded here.
